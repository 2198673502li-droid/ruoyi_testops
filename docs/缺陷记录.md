# 缺陷记录

> 目标：至少 3 条真实问题。不需要提交给上游，但要能对着面试官讲清「现象 / 复现 / 影响 / 建议」。

## 字段模板

| 字段 | 说明 |
|---|---|
| 编号 | BUG-001（按发现顺序） |
| 标题 | 一句话：什么场景下出现什么错误结果 |
| 模块 / 接口 | 例：用户管理 `POST /system/user` |
| 严重级别 | 致命 / 严重 / 一般 / 轻微（判据：是否影响数据正确性 > 是否影响主流程 > 是否仅体验） |
| 前置条件 | 账号、权限、数据状态 |
| 复现步骤 | 1) 2) 3)，可被第三人复现 |
| 期望 vs 实际 | 分两栏写，别混在一起 |
| 影响面 | 谁会遇到、影响多大 |
| 建议 | 修复方向，不要求给完整代码 |
| 证据 | 请求/响应报文、SQL 查询结果、截图 |

## 结构示例（勿删，替换内容）

```
BUG-001 逻辑删除后用户详情接口仍返回已删除数据
- 模块 / 接口：用户管理 GET /system/user/{userId}
- 严重级别：一般
- 前置条件：admin token，存在一条 del_flag='2' 的用户
- 复现步骤：
  1) DELETE /system/user/{userId} 删除用户
  2) GET /system/user/list?userName=xxx  → total=0（符合预期）
  3) GET /system/user/{userId}           → 仍返回 200 + 数据
- 期望：删除后详情返回 404 或业务码 500，不应返回已删除用户
- 实际：仍返回完整用户信息
- 影响面：数据已删除但可被直接 ID 访问，属越权/信息泄露风险
- 建议：详情接口加 del_flag='0' 过滤
- 证据：见 Allure 附件「失败现场」
```
