# 测试用例设计

> 这份文档是**面试时唯一能证明"你会设计用例"的物证**，比代码更重要。
> 规则：每条用例都要能答出「为什么它存在 / 覆盖哪个风险点 / 断言凭什么可信」。

## 一、四板斧（每个模块都按这 4 个维度过一遍）

| 维度 | 要覆盖的典型点 |
|---|---|
| 1. 鉴权 | 无 token / 错 token / 过期 token / 低权限 token / 已登出 token / 无角色用户 |
| 2. 参数 | 必填缺失 / 类型错误 / 超长 / 特殊字符（`' or 1=1 --`、`<script>`）/ 边界值（pageNum=0、pageSize=1000、日期区间） |
| 3. 业务状态 | 唯一性冲突 / 状态机（停用↔启用→删除）/ 逻辑删除后不可见 / 重复提交 / 依赖前置状态 / 超管保护 |
| 4. 数据一致性 | 接口返回 vs 数据库落库 vs 列表查询 vs Redis（token、pwd_err_cnt） |

## 二、覆盖矩阵（计划值，随实现更新）

| 模块 | P0 正向 | P1 异常/边界 | P2 权限/越权 | 小计 | 已实现 |
|---|---|---|---|---|---|
| 认证 | 2 | 4 | 2 | 8 | 0 |
| 用户 | 5 | 8 | 4 | 17 | 0 |
| 角色 | 4 | 5 | 3 | 12 | 0 |
| 部门 | 3 | 4 | 2 | 9 | 0 |
| 岗位 | 2 | 2 | 1 | 5 | 0 |
| 菜单 | 3 | 4 | 3 | 10 | 0 |
| 字典/参数 | 4 | 6 | 2 | 12 | 0 |
| 通知/日志/在线/任务 | 5 | 6 | 2 | 13 | 0 |
| 越权专题 | — | — | 12 | 12 | 0 |
| 健壮性专题 | — | 12 | — | 12 | 0 |

> 达不到 110 按 P0 → P1 → P2 砍。**宁可 60 条全绿且每条都讲得出理由，也不要 200 条没人看得懂的脚本。**

## 三、单条用例的记录模板

```markdown
### [模块]-[编号] 标题（一句话说清"做什么，验什么"）
- 优先级：P0 / P1 / P2
- 覆盖维度：鉴权 / 参数 / 业务状态 / 数据一致性（可多选）
- 前置条件：
- 步骤：1) ... 2) ...
- 断言：① HTTP 200 ② body.code == 200 ③ 数据库 del_flag='0' ④ 列表 total == 1
- 风险点：如果不测这条，会漏掉什么线上问题
```

## 四、示例（已实现的那种写法）

### 用户-U3-01 新增用户后：接口成功 + 库中落库 + 列表可查
- 优先级：P0　覆盖维度：业务状态 + 数据一致性
- 前置：admin token；`userName` 唯一化后缀 `autotest_<时间戳>`
- 断言：`code==200` → `sys_user` 有记录且 `del_flag='0'` → 列表接口 `total==1` → 详情 `userId` 与库中 `user_id` **字符串比较**
- 风险点：只断言接口 200 会漏掉「返回成功但没写库」类缺陷

## 五、断言规范

1. **不信单一信号**：写操作至少「接口 code + 落库 + 列表」两处交叉验证。
2. **Long 统一 `str()` 比较**：若依把 Long 序列化成字符串（`"1"` 不是 `1`）。
3. **不 sleep**：轮询 `wait_until`，最多 N 次，间隔 0.3s。
4. **数据可清理**：一律 `autotest_` 前缀 + teardown 兜底删除，跑完库里不留残留。
